Below is a **Business Requirements Document (BRD)** for implementing the new Brain-Centric Orchestration architecture in the existing FinAssist AI application while maximizing reuse of the current LangGraph workflow, agents, guardrails, RAG, and execution pipeline.

# Business Requirements Document (BRD)

# FinAssist AI – Brain-Centric Financial Intelligence Platform

# 1. Executive Summary

FinAssist currently provides:

* Conversational financial assistance
* RAG-based knowledge retrieval
* Agent-based transaction analytics
* Investment recommendations
* LangGraph workflow orchestration
* SQL-based transaction querying
* Guardrails and safety controls

The objective of this enhancement is to transform FinAssist into a **Brain-Centric Orchestrated AI System** where a central Brain dynamically selects and coordinates independent analytical capabilities.

The Brain will become the primary decision-maker and will orchestrate:

1. RAG
2. Agent Analytics Layer
3. Investment Analysis Engine

while reusing the majority of the existing LangGraph implementation.

---

# 2. Business Objectives

## Primary Goals

### Unified Intelligence

Provide a single reasoning layer capable of answering:

* Transaction questions

* Financial guidance
* Hybrid financial questions

---

### Personalized Responses

Leverage:

* User profile

Ensure all transaction data access continues through:

```text

```

Support:

* Follow-up questions

without requiring users to repeatedly provide information.

## Purpose

Convert follow-up conversations into standalone queries.

---

## Requirements

The Context Node shall:

* Read conversation history
* Resolve references
* Expand pronouns
* Generate complete standalone queries

---

## Example

User:

```text
How much did I spend on food this month?
```

User:

```text

```

```text
How much did I spend on shopping this month?
```

---

## Output

```json
{
  "standalone_query": "How much did I spend on shopping this month?"
```

# FR-4 Clarification Node

## Purpose

Determine whether sufficient information exists to answer the query.

---

## Inputs

* Standalone query
* User profile
* Conversation history

---

## Decision Logic

### If enough information exists

```json
{
  "needs_clarification": false
}
```

---

### If information is missing

```json
{
  "needs_clarification": true,
  "question": "What is your risk appetite?"
}
```

---

# Clarification Loop

The node shall support iterative questioning.

Flow:

```text
Question
 ↓
User Answer
 ↓
Question + Answer + History
 ↓
Clarification Node
 ↓

More Questions?
```

Repeat until:

```json
{
  "needs_clarification": false
}
```

---

# Clarification Options

Each clarification question shall return:

```json
{
  "question": "...",
  "options": [
      "Low",
      "Moderate",
      "High",
      "Other"
  ]
}
```

---

## Option Generation

Options shall be generated from:

* Entity schemas
* Database schemas
* Financial taxonomies
* Investment metadata

passed through the system prompt.

# FR-7 Brain Orchestrator

## Purpose

Central decision-making layer.

---

## Responsibilities

### Tool Selection

### Routing

### Execution Planning

### Context Aggregation

---

## Key Architectural Requirement

The Brain SHALL NOT execute tools directly.

The Brain SHALL produce an execution plan.

---

## Output Format

Example:

```json
{
  "tools": [
    {
      "tool": "agent_layer",
      "agent": "trend_agent",
      "args": {
        "category": "food",
        "period": "6_months"
      }
    },
    {
      "tool": "rag",
      "args": {
        "query": "food inflation"
      }
    }
  ]
}
```

---

## Execution Model

```text
Brain
 ↓
Execution Plan

Code Layer
 ↓

Execute Tool 1
Execute Tool 2
Execute Tool 3

 ↓

Return Results

 ↓

Brain
```

This aligns with the requirement:

> Brain first outputs what tools to call and with what arguments.

# 8. Success Criteria

The feature shall be considered complete when:

1. Brain successfully generates execution plans.
2. RAG can be invoked independently.
3. Agent Layer can be invoked independently.
4. Investment Analysis can be invoked independently.
5. Hybrid queries invoke multiple tools.
6. Clarification loop works end-to-end.
7. Follow-up queries become standalone queries.
8. SQL access only occurs through AST → Planner → Validator → Executor.
9. Existing guardrails remain functional.
10. Existing LangGraph components are reused wherever possible.

This approach minimizes refactoring by retaining the existing LangGraph foundation while introducing the Brain-Orchestrator, Context Node, Clarification Loop, Semantic Layer, and execution-plan-based tool routing.
